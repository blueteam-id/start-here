## What a branch is

A **branch** is a lightweight, movable pointer to a commit. It is not a separate copy of your files. That is why creating one is instant: Git copies nothing, it just adds a new named pointer next to `main`. See your current branch:

```bash
git branch
```

You should see `main`, the default branch Git created automatically (Lesson 1 set that name with `init.defaultBranch`). If you see `master` instead, your repository was created before that setting existed. Rename the branch once, and everything below works as written:

```bash
git branch -m master main
```

Now create and switch to a new branch:

```bash
git switch -c feature-notes
```

`switch` moves you to a branch, and `-c` creates it first. You are now on `feature-notes`, isolated from `main`. Nothing you commit here touches `main` until you merge it.

## Why branch instead of editing directly

That isolation is the whole point. On a branch, you can experiment, make a mess, and commit half-finished work without putting `main` at risk.

That is why "always branch first, never edit `main` directly" is close to a universal rule in software and security engineering. `main` is often what is deployed, or what detection rules are built from. Keeping it stable matters more than keeping any one branch tidy.

Make a change here to see the isolation:

```bash
echo "A note added on a branch." >> notes.txt
git add notes.txt
git commit -m "Add a branch-only note"
git switch main
cat notes.txt
```

On `main`, `notes.txt` does not have the new line. It only exists on `feature-notes` until you merge it.

## Merging branches together

Bring the branch's work into `main`:

```bash
git merge feature-notes
```

- If `main` had not changed since you branched, Git does a **fast-forward merge**: it just moves the `main` pointer forward. No new commit is needed.
- If both branches had new commits, Git creates a **merge commit** that joins the two histories.

## When Git cannot decide for you: merge conflicts

A **conflict** happens when two branches changed the same lines in different ways. Git cannot guess which version you want. Create one on purpose:

```bash
git switch -c conflict-demo
echo "Branch version of this line." > conflict.txt
git add conflict.txt
git commit -m "Add conflict.txt on conflict-demo"
git switch main
echo "Main version of this line." > conflict.txt
git add conflict.txt
git commit -m "Add conflict.txt on main"
git merge conflict-demo
```

Git stops and marks the file with conflict markers:

```
<<<<<<< HEAD
Main version of this line.
=======
Branch version of this line.
>>>>>>> conflict-demo
```

To fix it, you need to edit the file. If you have never edited a file from the terminal, `nano` is the simplest editor and works on macOS, Linux, WSL, and Git Bash:

```bash
nano conflict.txt
```

Move around with the arrow keys and type as usual. To save, press `Ctrl+O`, then `Enter`. To exit, press `Ctrl+X`. (On Windows you can also run `notepad conflict.txt` from Git Bash, edit, save, and close the window.)

Decide what the final content should actually be: keep one version, the other, or something that combines both. Delete the `<<<<<<<`, `=======`, and `>>>>>>>` marker lines, save, then finish the merge:

```bash
git add conflict.txt
git commit -m "Resolve conflict.txt merge"
```

Resolving a conflict is a real decision, not a mechanical step. In a firewall or detection rule, two good changes merged carelessly can cancel each other out, or reopen something an earlier change had closed. Give a conflict the same care as writing the rule in the first place. It is not an obstacle to clear as fast as possible.

### What to notice

- A branch is just a pointer, so it costs almost nothing. That is what makes "always branch first" practical.
- A fast-forward merge only moves a pointer. A merge commit records that two histories joined, which is useful information later.
- A merge conflict is Git refusing to guess. Resolve it carefully, not quickly.
