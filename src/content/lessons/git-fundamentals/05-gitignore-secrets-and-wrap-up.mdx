## .gitignore: what should never be tracked

Not everything in a project folder belongs in version control: build output, junk files the OS creates, and above all, **anything secret**. A `.gitignore` file lists files or patterns Git should never track. Create one:

```bash
echo ".env" > .gitignore
git add .gitignore
git commit -m "Add .gitignore for local secrets"
```

Now create a file that `.gitignore` protects:

```bash
echo "API_KEY=fake-example-not-a-real-secret" > .env
git status
```

`.env` does not appear at all, not even as untracked. `.gitignore` is working. The best defense against committing a secret is never letting Git see the file that holds it.

## The uncomfortable truth about secrets already committed

This catches people out constantly in real projects. If a secret was ever committed and pushed, **deleting it in a later commit does not remove it**. It is still there, intact, in every earlier commit. Anyone with a copy of the repository can recover it. Rewriting history can remove it, but anyone who already cloned or forked the repository still has their own copy.

See this for yourself, safely, on your own machine. Commit a fake secret on purpose:

```bash
echo "PASSWORD=not-a-real-secret-either" > leaked.txt
git add leaked.txt
git commit -m "Oops, commit a secret"
```

Now "discover" it the way anyone with access to the history could. Find the commit's hash in the first command's output, then show that commit:

```bash
git log --oneline
git show <commit-hash-from-above>
```

The secret is right there in the commit's diff, as if you were investigating this repository after the fact. Deleting `leaked.txt` in a new commit would hide it from the current files, but `git show` on the earlier commit would still reveal it.

So the real fix for a leaked credential is: **rotate or revoke it immediately.** Treat it as compromised from the moment it was pushed anywhere. Quietly removing the file does not solve the problem.

Clean up now that the point is made:

```bash
rm leaked.txt
git add leaked.txt
git commit -m "Remove leaked.txt from the working tree (history still has it)"
```

## What you now know

Four lessons ago, you had never run `git init`. Here is what you covered since:

1. **What Is Git, and Why Security Teams Live in It.** Git is a distributed version control system. Its hard-to-fake history is why infrastructure as code and detection as code rely on it as an audit trail.
2. **Making and Tracking Changes.** Working directory, staging area, and commit are separate steps on purpose. `git log` tells you who and when; `git diff` tells you exactly what.
3. **Branching and Merging.** A branch is a cheap, isolated pointer, which is why "always branch, never edit `main` directly" works. A merge conflict needs real judgment, not a quick guess.
4. **Undoing Mistakes Safely.** `git restore` undoes what was never committed. `git revert` undoes shared work without erasing the record. `git reset` rewrites history, which is dangerous once anyone else has a copy.

Think in snapshots, isolate risky changes on branches, read history like evidence, and undo mistakes without hiding them. These are the daily reflexes of anyone who works seriously with Git.

## Combined hands-on exercise: reviewing a small project's history

This exercise chains the whole track into one small scenario: you are handed a small project, asked to check its history for anything that should not be there, and then to finish cleanly.

Start by looking at the history of your practice repository:

```bash
git log --oneline
```

Read it like an investigator. Which commits look ordinary? One should stand out: "Oops, commit a secret". Confirm it is still fully visible:

```bash
git show --stat HEAD~1
```

`HEAD~1` means "one commit before the latest". If your history is different, use that commit's hash instead; the goal is to land on the "Oops" commit. This confirms again that deleting a file later never erases it from history. In a real project, this is the moment you would go rotate the exposed credential, not just note that the file is gone.

Finish with the right branch habit. Make one more small change properly, branch, commit, and merge, so the last entries in your history are a clean example of the workflow from this track:

```bash
git switch -c wrap-up-note
echo "Track complete." >> notes.txt
git add notes.txt
git commit -m "Mark Git Fundamentals complete"
git switch main
git merge wrap-up-note
git log --oneline
```

You walked the whole path: finding a leaked secret in history, understanding why deleting the file is not the fix, and closing with the branch-and-merge habit from Lesson 3. Nothing ever left your own machine.
