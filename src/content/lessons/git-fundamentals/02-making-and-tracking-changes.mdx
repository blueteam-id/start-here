## Turning a folder into a repository: git init

A plain folder becomes a Git repository the moment you run `git init` inside it. Go to your practice folder first, then run it:

```bash
cd ~/git-fundamentals
git init
```

The `cd` matters. `git init` turns whatever folder you are standing in into a repository, and you do not want that to be your home folder by accident.

This creates a hidden `.git` folder. It holds the entire history you are about to build: every commit, every version of every file. Deleting that one folder is how you truly lose everything Git has tracked. Remember that before running any cleanup command carelessly.

## The three places a change can be

Git sees a file in one of three places:

- the **working directory**: the files you see and edit normally,
- the **staging area**: changes you have marked as ready to save,
- the **repository**: changes you have committed, permanently.

Create a file and watch it move through them:

```bash
echo "Practice notes for Git Fundamentals" > notes.txt
git status
```

`git status` reports `notes.txt` as **untracked**: Git sees the file, but is not tracking it yet.

## Staging and committing: git add, git commit

```bash
git add notes.txt
git status
```

The file now shows as staged, ready to save. Commit it:

```bash
git commit -m "Add practice notes"
```

A **commit** is a permanent snapshot that cannot be changed. It records the exact state of every staged file, plus:

- your name and email from Lesson 1,
- a timestamp,
- a message,
- a link to the commit before it.

That metadata is why Lesson 1 asked for a real name: it is attached to every commit you ever make.

Write commit messages as a short, clear summary of what changed and why. Avoid "fix" or "update". A future reader, maybe you, maybe someone investigating an incident, has only the message and the diff to go on.

## Reading history: git log

```bash
git log
```

Each entry shows the commit's unique hash, author, date, and message. When the output is longer than your screen, Git shows it one page at a time and your prompt seems to disappear. Use the arrow keys to scroll, and press `q` to quit back to your prompt. The same applies to `git diff` and `git show` later on.

The shorter view is often more useful day to day:

```bash
git log --oneline
```

For "who touched this file, and when?" during an investigation, `git log --follow -- notes.txt` shows every commit that changed that one file, even across a rename.

## Seeing exactly what changed: git diff

Edit the file and compare:

```bash
echo "A second line." >> notes.txt
git diff
```

`git diff` shows the exact lines added (`+`) and removed (`-`). Code review and configuration-drift tools are built on the same idea. Unexpected or unauthorized changes get caught by someone, or something, reading a diff, not by rereading the whole file every time.

Stage and commit this change too, then look at your history:

```bash
git add notes.txt
git commit -m "Add a second line to practice notes"
git log --oneline
```

You should see two commits, with the oldest at the bottom.

### What to notice

- Staging lets you build a commit on purpose, file by file or change by change, instead of saving everything at once.
- `git log` answers "who, and when". `git diff` answers "exactly what". Real investigations usually need both.
- Write commit messages for a reader with no other context. During an incident, that reader may be you.
