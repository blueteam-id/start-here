## Four ways to undo, and why they are not interchangeable

Git has several ways to undo something. Picking the wrong one causes real problems, so learn what each does before you need it in a hurry:

- **`git restore`** throws away **uncommitted** changes to a file, back to the last commit. Use it for a change you have not saved yet and do not want.
- **`git reset`** moves your branch pointer backward, which **rewrites** local history. It is safe on commits only you have seen. It is dangerous on anything you have shared, because commits other people already have can vanish from your side of the story.
- **`git revert`** creates a **new commit** that undoes an earlier one. The mistake and the fix both stay visible. It is safe on shared, already-pushed history.
- **`git stash`** temporarily **shelves** uncommitted changes without committing them, so you can switch tasks and come back later.

## Try `git restore` on an unwanted change

```bash
echo "A line I did not mean to add." >> notes.txt
git restore notes.txt
cat notes.txt
```

The line is gone. It was never committed, so there is nothing to undo later.

## Why `git revert`, not `git reset`, on anything shared

First, commit a real mistake:

```bash
echo "This line is wrong and needs undoing." >> notes.txt
git add notes.txt
git commit -m "Accidentally commit an incorrect note"
```

Now undo it the safe way:

```bash
git revert --no-edit HEAD
git log --oneline
```

`--no-edit` tells Git to use its standard message ("Revert ...") for the new commit. Without it, Git opens a text editor so you can write the message yourself.

Your history now shows **both** commits: the mistake, and a new commit that undoes it. Nothing was erased. `git reset` would have moved the branch pointer back instead, and the mistaken commit would have disappeared from the visible history.

This matters more than it seems. A history with commits quietly missing, especially on a branch others already pulled, looks a lot like someone covering their tracks, even when nobody meant harm. That is why force-pushing and history rewrites are often blocked on shared, protected branches. `git revert` keeps the record honest: "this was wrong, and here is the fix", both visible. It is the same instinct as never clearing an audit log to hide a problem.

## git stash for "I need to switch away right now"

```bash
echo "Half-finished work, not ready to commit yet." >> notes.txt
git stash
git status
```

Your change is shelved, and `notes.txt` is back to its last committed state. Bring the change back when you are ready:

```bash
git stash pop
```

If you ever shelve more than one thing, `git stash list` shows them all.

### What to notice

- `git restore` undoes what was never committed. `git revert` undoes what was committed and shared. Using the wrong one is how real history gets lost.
- A history with an honest mistake-and-fix pair, both visible, is more trustworthy than one where the mistake quietly disappeared.
- `git stash` means "not now, but do not lose this". Finished work should be committed instead.
