## What a "remote" is

A **remote** is a named pointer to another copy of your repository, almost always one on GitHub or GitLab. When you clone a repository, Git names its source `origin`, the default name for "the remote I work with".

## Connecting to your practice repository

On your practice repository's GitHub page, click the green **Code** button and copy the URL. HTTPS is the simplest option to start with. Then, on your own machine:

```bash
cd ~
git clone <the-url-you-copied>
cd git-practice
```

The `cd ~` first matters: if your terminal is still inside the `git-fundamentals` folder from the previous track, cloning there would put one repository inside another, which confuses Git. (Windows users: keep using Git Bash, as in Git Fundamentals.)

`git clone` downloads the whole repository, history included, and sets up `origin` to point back at it. Cloning a public repository needs no sign-in. Make a local change and commit it the way Git Fundamentals taught you:

```bash
echo "A change made locally." >> README.md
git add README.md
git commit -m "Update README from local clone"
```

### Before your first push: sign in once

Uploading is different from downloading. The first time you push, the platform needs to know you are allowed to write to this repository. GitHub and GitLab **do not accept your account password** here, so typing it in will fail with "Authentication failed". Use one of these instead:

- **Windows (Git Bash):** Git for Windows includes Git Credential Manager. On your first push, a browser window opens and asks you to sign in to GitHub. Approve it, and Git remembers you.
- **macOS, Linux, and WSL:** create a **personal access token (PAT)**, a password-like key made for one purpose. On GitHub: **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**. Give it a short expiry (7 days is plenty), choose **Only select repositories** and pick `git-practice`, and under **Repository permissions** set **Contents** to **Read and write**. Copy the token. When `git push` asks for a username, type your GitHub username. When it asks for a password, paste the token. (The terminal shows nothing while you paste. That is normal.)
- **GitLab:** create a token under **Edit profile → Access tokens** with the `write_repository` scope, and use it the same way.

On Linux and WSL, Git will ask for the token on every push unless you let it remember for a while. This keeps it in memory for one hour, never on disk:

```bash
git config --global credential.helper 'cache --timeout=3600'
```

<Callout type="warning">

Treat a token exactly like a password: never paste it into a chat, a file in the repository, or a screenshot. Lesson 4 explains why tokens are safer than passwords (you can limit them and revoke them one by one).

</Callout>

Now push:

```bash
git push origin main
```

`git push` uploads your new commit to the remote. Refresh the repository's page on GitHub: your change is there.

## Fork vs. clone

- **Cloning** copies a repository to your own machine. It is a Git operation and works on any repository you can read.
- **Forking** creates your own copy of someone else's repository, under your account, on the platform itself. It is a GitHub/GitLab feature, not a Git one.

You fork when you want to propose a change to a project you cannot write to. The steps: fork it, clone your fork, branch, commit, push to your fork, then open a pull request asking the original project to take your change. This **fork-and-pull** pattern is how almost all open-source contribution works.

## The security wrinkle: running untrusted code from a fork

Here is a real, current issue worth understanding as a concept, without trying it.

Imagine a CI pipeline that runs automatically on every pull request, including pull requests from forks by complete strangers. Imagine that pipeline can also see the repository's secrets, or has elevated permissions. An attacker can then submit a pull request designed to abuse that combination: for example, to steal a secret the pipeline can see, or to tamper with a build step. This is well known enough in GitHub Actions and GitLab CI to have a name: a **"pwn request"**.

That is why GitHub requires a maintainer to approve the first CI run on a pull request from a first-time contributor. It is also why well-configured pipelines do not give secrets to workflows started by fork pull requests. You do not need to know how to exploit this to see why the approval step exists. It is a deliberate pause, placed exactly where an untrusted contribution meets real permissions, like a UAC prompt between a program and admin access.

## Fetch vs. pull

```bash
git fetch origin
```

`fetch` downloads what is new on the remote **without changing your branches**, so you can look before you merge anything. `git pull` is `git fetch` followed immediately by `git merge`. That is convenient most of the time. But fetch first is the right habit when you want to review someone else's changes before mixing them into your own work.

### What to notice

- A clone copies a repository you can read. A fork makes your own copy of one you cannot write to, so you can propose changes without write access.
- A pull request from an unknown contributor is normal. That is why CI pipelines need guardrails on what that pull request's code may touch.
- `git fetch` lets you look before you leap. `git pull` leaps right away.
