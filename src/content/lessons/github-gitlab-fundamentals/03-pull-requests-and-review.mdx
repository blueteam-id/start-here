## Opening a pull request

From inside your `git-practice` folder, create a branch, make a change, and push it:

```bash
git switch -c add-practice-notes
echo "Notes from the GitHub/GitLab Fundamentals track." > notes.txt
git add notes.txt
git commit -m "Add practice notes"
git push -u origin add-practice-notes
```

On your repository's GitHub page, you will see a prompt to open a pull request from this branch. Click it, give it a short title, and open it against `main`.

A **pull request** (GitLab: **merge request**) is a proposal: "please merge this branch into that one". It shows the change as a diff, with a conversation attached: comments, review approvals, and automated checks, all about that one change. It is the `git diff` idea from Git Fundamentals Lesson 2, turned into something other people can discuss before anything is merged.

## Why review is a security control, not just a style check

The real job of code review is to catch a problem before it reaches `main`: a bug, an accidental secret, or a deliberately malicious change.

Review fails in one well-known way. A reviewer under time pressure sees a large or urgent-looking diff and approves it with a quick "looks good to me", without reading every changed line. That is a social-engineering pattern. It uses the same instinct a phishing email uses, just aimed at a tired reviewer instead of an inbox.

A few habits keep review doing its job:

- Read the full diff, not just the description of what it should do.
- Pay **more** attention to changes in CI configuration, dependencies, or build scripts, because those run with real permissions.
- Question any file that changed but should not have needed to for this fix.
- Treat "trust me, it's fine" as a reason to look more closely.

## Branch protection rules

On the repository's **Settings → Branches** page, you can add a protection rule for `main`. For example, it can require:

- at least one approving review before merging,
- passing CI checks before merging,
- no direct pushes: everyone, including admins, goes through a pull request.

This turns the "always branch, always review" habit from Git Fundamentals into an enforced rule, instead of something that depends on everyone remembering.

GitHub currently offers two screens for this: a classic **branch protection rule**, and newer **rulesets** (under **Settings → Rules → Rulesets**). They do the same job for this track; use whichever your repository page shows. On GitLab, the equivalent is **Settings → Repository → Protected branches**.

One thing to know before you try it on your solo practice repository: **you cannot approve your own pull request.** A rule that requires one approval works on a team, because someone else reviews. On a repository where you are the only person, it would block every merge. So for practice, require a pull request before merging but set the required approvals to **0**. You still get the important part, no direct pushes to `main`, without locking yourself out. You will set this up in the wrap-up lesson.

Now merge your own pull request in the web UI. Then look at the repository's commit history: it reads just like `git log`, because that is what it is.

### What to notice

- A pull request is a `git diff` made visible and discussable before it becomes permanent. It is part of the Git workflow you already know, not something separate.
- A rushed approval of a diff nobody really read is a known, real way problems get through review.
- Branch protection turns a good habit into a rule everyone must follow, including people who would otherwise be trusted to skip it.
