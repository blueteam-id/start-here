## What CI is

**Continuous Integration (CI)** means running something automatically, such as tests, a build, or a security scan, every time code changes. Usually that is on every push and every pull request.

The instructions live in a file committed to the repository itself:

- `.github/workflows/*.yml` for GitHub Actions,
- `.gitlab-ci.yml` for GitLab CI.

This site's own repository works this way. Its workflow file defines a job that installs dependencies, runs the tests, and builds the site, automatically, whenever someone opens a pull request.

## Why CI/CD is one of the highest-value targets in modern security

Put Lessons 2 and 4 together and the picture is clear. CI:

- runs **automatically**,
- often holds **real secrets and permissions**,
- can be **started by a pull request**, which an outside contributor can submit.

Automatic execution, real access, and a trigger an attacker can influence: that combination is why CI/CD security has become its own specialty inside software supply-chain security.

A few habits worth knowing at foundation level, even before you configure a pipeline yourself:

- **Pin dependency and action versions** instead of trusting "latest", so a compromised upstream update cannot quietly change what your pipeline runs.
- **Review changes to workflow files as carefully as code changes.** A workflow file is code, with real permissions.
- **Require approval before running CI on a first-time contributor's pull request**, the guardrail from Lesson 2.

## What you now know

Four lessons ago, your code only lived on your own machine. Here is what you covered since:

1. **What GitHub and GitLab Add on Top of Git.** Hosting, a web UI, and collaboration on top of plain Git. Account security on these platforms is repository security.
2. **Remotes and the Fork-and-Pull Workflow.** A fork lets you propose changes without write access. A CI pipeline that runs fork pull requests with real secrets is a known, named risk.
3. **Pull Requests, Code Review, and Branch Protection.** A pull request makes a diff discussable before it is permanent. Branch protection turns "always review" from a habit into an enforced rule.
4. **Access Control and Secrets.** Least privilege applies to repository access like anywhere else. Secrets belong in the platform's secret store, never in the code.

Know what the platform adds, use forks and pull requests on purpose, review changes like they matter, and keep access and secrets locked down. That is what collaborating on code at scale requires.

## Combined hands-on exercise: a mini repository security check

This exercise chains the whole track into one small scenario: a quick security pass on your own practice repository, the way you would check any project you were just given access to.

1. Open your practice repository's **Settings → Collaborators** (or **Members** on GitLab) and check who has access, and at what level. On a solo practice repository it should be only you. Confirm it rather than assume it.
2. Open **Settings → Branches** (or **Settings → Rules → Rulesets**) and confirm whether `main` has any protection rule. If not, add one now that requires a pull request before merging, with required approvals set to **0**, as Lesson 3 explained. On a real team you would require at least one approval; on a solo repository that would stop you from ever merging, because you cannot approve your own pull request.
3. Open the **Settings → Secrets** page from Lesson 4 again, and confirm it is empty, as a brand-new practice repository should be.
4. Finally, make one more small change the right way: branch, commit, push, open a pull request, and merge it. Your history then ends with a clean example of the full workflow. Start from an up-to-date `main`, since Lesson 3's pull request was merged on the website, not on your machine:

```bash
git switch main
git pull
git switch -c wrap-up-check
echo "GitHub/GitLab Fundamentals complete." >> notes.txt
git add notes.txt
git commit -m "Mark GitHub/GitLab Fundamentals complete"
git push -u origin wrap-up-check
```

Open and merge the pull request in the web UI, as in Lesson 3.

You walked the whole path: checking who has access, confirming branch protection, confirming no secrets are where they should not be, and finishing with the branch-review-merge workflow the track is built around.
