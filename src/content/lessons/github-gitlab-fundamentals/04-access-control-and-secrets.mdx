## Permission levels

Both platforms let you give different people different access to each repository, instead of all or nothing.

- **GitHub** roles go from **read** (view and clone), through **triage** and **write** (push, manage issues) and **maintain**, up to **admin** (full control, including who else has access).
- **GitLab** uses Guest, Reporter, Developer, Maintainer, and Owner.

The names differ; the idea is the same. This is the **principle of least privilege**, applied to source code. Give each person the access their work needs, and no more. Review that access from time to time instead of assuming it is still right.

## Why account security is repository security

An account with write access to a repository is, in practice, a key to that repository. So decisions about account security are decisions about repository security:

- **Two-factor authentication** (Lesson 1) on every account with any write access. No exceptions for "trusted" people.
- **Personal access tokens (PATs)** instead of your password for the command line and APIs, like the token you may have created in Lesson 2. If a token leaks, you revoke just that token without changing your password. You can also limit a token to the permissions it needs, and give it an expiry date instead of letting it live forever.
- **The real lesson:** a compromised maintainer account is effectively a compromised project, because everyone who pulls from it trusts every push made under that name. This is how a real category of modern incident works: an attacker steals one maintainer's credentials and pushes a tampered update that everyone downstream trusts by default.

## Secrets belong in the platform's secret store, never in code

This continues Git Fundamentals Lesson 5. Platforms have a place to store secrets, like API keys, so they never appear in the code:

- **GitHub:** repository or organization **Settings → Secrets and variables → Actions**.
- **GitLab:** **Settings → CI/CD → Variables**.

The values are given to CI runs when they execute, and are never written into the repository.

The rule from before still applies: if a secret ever leaks into a repository's history, public or private, deleting the file afterward does not undo the leak. The real fix is to **rotate or revoke the credential immediately**, as soon as you know it was exposed.

Now open your practice repository's secrets settings page and just look, without changing anything, so you know where it is when you need it.

### What to notice

- Access levels let you give people the access their work needs, not the most convenient blanket option.
- One compromised maintainer account is, in practice, one compromised project, because everything pushed under that account is trusted downstream.
- The secrets store exists so a credential never has to appear in code. It is the strongest version of the `.gitignore` habit from the previous track.
