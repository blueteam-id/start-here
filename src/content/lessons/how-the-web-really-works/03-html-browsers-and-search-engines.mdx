## Three languages in every page

A web page is built from three kinds of files:

- **HTML** describes the **content and structure**: headings, paragraphs, links, images, forms.
- **CSS** describes the **look**: colors, fonts, layout.
- **JavaScript** is **code** that runs in your browser: menus, live updates, form checks.

The server sends them, and your browser puts them together. That last point matters for security: JavaScript from a website runs **on your machine**, inside your browser. Browsers keep each site's code fenced off from other sites, but a malicious or compromised script still runs with everything that one site can see, including what you type into it.

## Hands-on: build and inspect a tiny page

Create a practice folder and a 10-line web page:

Your browser opens the page from a `file://` address: no server, no network. Now, on that page:

1. Right-click and choose **View Page Source**. You see exactly the HTML you wrote.
2. Open DevTools (`F12`), go to the **Console** tab, type `document.title` and press Enter. JavaScript read the page's title.
3. Type `document.querySelector('h1').textContent = 'Changed by JavaScript'` and press Enter. The heading changes. Reload the page and it is back: the change only happened in your browser, not in the file.

That last step is the key idea: whatever runs in your browser can change what you see and read what is on the page.

## Search engines: crawl, index, answer

A **search engine** works in three steps:

1. **Crawl**: programs called **crawlers** (or bots) follow links from page to page and download what they find.
2. **Index**: the engine stores what each page contains, so it can look it up fast.
3. **Answer**: when you search, it ranks matching pages from its index.

Anything a crawler can reach by following public links can end up in search results. That includes things that were never meant to be public: a forgotten test page, a document uploaded to a public folder, a login page for an internal tool.

## robots.txt is a request, not a lock

A site can publish `/robots.txt` to ask crawlers not to visit certain paths. Look at one:

<CodeTabs>
  <Fragment slot="macos">

```bash
curl -s https://en.wikipedia.org/robots.txt | head -n 30
```

  </Fragment>
  <Fragment slot="linux">

```bash
curl -s https://en.wikipedia.org/robots.txt | head -n 30
```

  </Fragment>
  <Fragment slot="windows">

```powershell
curl.exe -s https://en.wikipedia.org/robots.txt | Select-Object -First 30
```

  </Fragment>
</CodeTabs>

Each `User-agent:` line names a crawler, and `Disallow:` lines list paths it is asked to skip. Polite crawlers obey. Attackers' tools do not, and some read `robots.txt` first, because it can point straight at the paths a site wanted to hide.

<Callout type="warning" title="Search operators: only on your own organization">

Search engines support operators such as `site:example.com` (only this site) and `filetype:pdf` (only this file type). Defenders use them to find what their **own** organization exposed by mistake. Using them to dig for other people's exposed data takes you into the territory Security Concepts Lesson 4 warns about.

</Callout>

### What to notice

- HTML is content, CSS is looks, JavaScript is code that runs in your browser.
- Whatever runs in your browser can read and change the page, which is why malicious scripts are dangerous.
- Search engines index anything reachable by public links, including mistakes.
- `robots.txt` asks politely; it hides nothing, and can even advertise what a site wanted hidden.
