## Every running program is a process

Every program running on your machine right now is a **process**: your terminal, your browser, whatever is showing you this lesson. A process is a running copy of a program. It has its own memory, its own share of CPU time, and a unique number called a **PID** (process ID). Linux juggles hundreds of them, switching so fast that they all seem to run at once.

Listing what runs, watching it live, and stopping something that misbehaves are basic skills for anyone running a Linux system. They are also some of the most direct defensive skills in this track. An unfamiliar process burning CPU, or one making network connections it should not, is often an early sign of a compromise:

- A **cryptominer** shows up as a process keeping the CPU near 100%, day and night.
- A **reverse shell** shows up as a normal-looking process holding a connection to somewhere it should not talk to.

You can only notice either one if you already know what "normal" looks like on your machine.

## ps aux: a snapshot of every process

```bash
ps aux
```

`ps` prints a snapshot of every process at the moment you run it. The columns that matter most:

- **USER**: the account that owns the process. A process you did not start, running as root or another user, deserves a second look.
- **PID**: the process ID. You need it to stop the process.
- **%CPU**: how much CPU it uses. Sitting at 0.0 is normal. Stuck near 100%, from something you do not recognize, is not.
- **%MEM**: how much memory it uses.
- **COMMAND**: the command that started it, with its arguments. Usually the fastest way to tell what a process is.

You will often see another set of flags that shows the same information:

```bash
ps -ef
```

`-ef` is the traditional Unix style. `aux` is the BSD style, which is more common on Linux. The columns are laid out a little differently, but the information is the same. Pick one and get used to reading it.

## top: watching processes live

`ps` is a snapshot. `top` is a live view that keeps updating, with the busiest processes at the top:

```bash
top
```

The columns are close to `ps`: PID, user, %CPU, %MEM, and command, refreshed every few seconds. Use it when something feels slow and you want to see, right now, what is using resources. Press `q` to quit.

If `htop` is installed, try it too. It shows the same information with colors, easier scrolling, and a clearer process tree. It is not installed everywhere, which is why you learn `top` first.

## kill: stopping a process

With a PID from `ps` or `top`, you can ask a process to stop:

```bash
kill <pid>
```

By default, `kill` sends a polite request: the `TERM` signal. A well-behaved program catches it, closes its files, saves what it needs to, and exits cleanly.

Sometimes a process ignores the request, or is too stuck to respond. For that there is a forceful version:

```bash
kill -9 <pid>
```

`-9` sends `SIGKILL`. The operating system ends the process immediately, with no chance to clean up. Use a plain `kill` first and give it a moment. Only use `kill -9` if the process really will not stop, because skipping cleanup can leave half-written files behind.

### Try it safely: kill a process you started yourself

Do not practice by killing a random PID from your real process list. You might stop something you need, like your shell or your browser. Start a harmless process of your own instead:

```bash
sleep 300 &
```

`sleep 300` does nothing for five minutes. The `&` runs it **in the background**, so you get your prompt back right away. The shell prints a job number and a PID. You can also get that PID from the special variable `$!`, which holds the PID of the last background command:

```bash
echo $!
```

Confirm it is running, stop it, and confirm it is gone:

```bash
ps aux | grep sleep
kill $!
ps aux | grep sleep
```

The first `ps` shows the `sleep` process. After `kill`, the second `ps` shows only the `grep sleep` command matching its own name, which is normal. That is the whole workflow: list, identify, stop, confirm. You practiced it on a process only you created.

## Installing software: package managers

Software on Linux (and macOS) is usually installed with a **package manager**. It downloads a program and everything the program depends on, keeps track of what is installed, and can remove it cleanly later. That is different from downloading an installer from a website. Nearly every Linux server you will touch is managed this way.

This section is **for reference only**, so you recognize the commands later. Do not run them now: `apt install` and the Homebrew installer both need elevated privileges (`sudo` on Linux, an admin password on macOS), which this track does not use.

<CodeTabs>
  <Fragment slot="macos">

```bash
# install a package with Homebrew
brew install <package>
```

Homebrew is not built into macOS. It is a one-time install from [brew.sh](https://brew.sh), and the installer asks for your admin password.

  </Fragment>
  <Fragment slot="linux">

```bash
# install a package on Debian/Ubuntu-family systems (and WSL Ubuntu)
apt install <package>
```

`apt install` always needs `sudo` (`sudo apt install <package>`), because installing software for the whole system is a privileged action.

  </Fragment>
</CodeTabs>

You will meet `apt` on Debian, Ubuntu, and everything built on them, including Ubuntu under WSL. On the Red Hat family (Fedora, CentOS, RHEL, Rocky Linux, and similar), the tools are `dnf` (modern) and `yum` (older). The commands look similar, for example `dnf install <package>`, but this lesson does not walk through them.

Package managers matter to defenders too. When you investigate a server that may have been tampered with, an early step is to check which packages are installed, and when. An unexplained package, or a group of installs around the time something went wrong, is a strong lead.

### What to notice

- `ps aux` (or `ps -ef`) is a snapshot of every process. Read USER, PID, %CPU, %MEM, and COMMAND first.
- `top` shows the same live, sorted by CPU, and `q` quits. `htop` is a friendlier option where installed.
- `kill <pid>` asks a process to exit cleanly. `kill -9 <pid>` forces it, and is only for when a plain `kill` fails.
- Package managers (`brew` on macOS, `apt` on Debian/Ubuntu and WSL, `dnf`/`yum` on Red Hat family) install and track software in a way you can undo.
- An unknown process using CPU or the network, and an unexplained package, are both worth investigating on any system you look after.
