## Reading ls -l

Create a file to look at:

```bash
touch notes.txt
ls -l notes.txt
```

You will see a line like this:

```
-rw-r--r-- 1 you you 0 Jan 10 08:00 notes.txt
```

The first column, `-rw-r--r--`, is the **permission string**. Learn to read it on sight: it is the first thing to check on any file that matters.

The **first character** is the file type. `-` means a regular file. `d` means a directory.

The **next nine characters** are three groups of three:

- Characters 2-4: what the **owner** (the user who owns the file) can do.
- Characters 5-7: what the **group** (a set of users who share access) can do.
- Characters 8-10: what **other** (everyone else on the system) can do.

Inside each group, the letters mean:

- `r` = read (view the contents)
- `w` = write (change or delete the contents)
- `x` = execute (run it as a program or script)

A `-` in a position means that permission is missing. So `-rw-r--r--` reads: a regular file; the owner can read and write; the group can only read; everyone else can only read.

### The numeric (octal) equivalent

Each `rwx` group also has a number. Add up the values of the permissions that are present:

- `r` = 4
- `w` = 2
- `x` = 1

So `rw-` is `4 + 2 = 6`. `r-x` is `4 + 1 = 5`. `r--` is `4`. `rwx` is `4 + 2 + 1 = 7`.

One digit per group, in owner-group-other order, gives a three-digit number. `-rw-r--r--` is `644`. `-rwxr-xr-x` is `755`. You will see these two numbers constantly, and now you know what they mean instead of memorizing them.

## chmod: changing permissions

`chmod` changes a file's permissions. It has two forms, and both are worth knowing.

### Symbolic form

The symbolic form adds or removes specific permissions and leaves the rest alone. You write:

- a **target**: `u` (owner), `g` (group), `o` (other), or `a` (all),
- an **operator**: `+` to add, `-` to remove,
- a **letter**: `r`, `w`, or `x`.

```bash
chmod u+x notes.txt
ls -l notes.txt
```

That adds execute for the owner only. `-rw-r--r--` becomes `-rwxr--r--`, and the group and other permissions do not change. Remove it the same way:

```bash
chmod u-x notes.txt
ls -l notes.txt
```

### Numeric form

The numeric form sets the whole permission string at once, using the numbers from above:

```bash
chmod 644 notes.txt
ls -l notes.txt
```

That sets `notes.txt` to exactly `-rw-r--r--`. Try another number and watch the letters change:

```bash
chmod 755 notes.txt
ls -l notes.txt
```

Now the owner can read, write, and execute. Group and other can read and execute, but not write. `755` is the standard setting for a script or program that everyone may run but only the owner may edit. Set the file back to a plain, non-executable file:

```bash
chmod 644 notes.txt
```

These numbers are one of the first things checked in a real penetration test. Picture a script owned by root that is **world-writable** (a careless `666` or `777`). Any user on the machine can change what root is about to run. That is a textbook **privilege escalation** path. Reading `644`, `755`, and an overly open `666` at a glance is how a defender spots it first.

## Who are you? Users and groups

Permissions only make sense once you know which user you are, and which groups you belong to. Ask the system:

```bash
whoami
id
groups
```

`whoami` prints your username. `id` prints your user ID (a number, `uid`), your main group, and every group you are in. The owner and group columns in `ls -l` are these same names.

Every account on the system, including the ones the OS uses for its own services, is listed in one file. It is safe to read:

```bash
head -n 5 /etc/passwd
```

Each line is one account, with fields separated by `:`: the username, an `x` or `*` (the password itself is stored elsewhere, in a file ordinary users cannot read), the user ID, the group ID, a description, the home folder, and the login shell. Account `root` always has user ID `0`. On a real investigation, an unexpected second account with user ID `0` is a serious red flag, because it is another root. (On macOS this file only lists the system's own service accounts; your account is stored elsewhere.)

You will also see `sudo` everywhere online. It means "run this one command as root". This track never uses it, because running as root is exactly when a typo can damage the system. When a guide tells you to put `sudo` in front of a command, stop and ask whether that command really needs to change the system, and whether you trust where the instruction came from.

## chown: ownership, conceptually

Every file has an **owner** (a user) and a **group**. `ls -l` shows both between the permission string and the size. In the example above, `you you` means owner `you`, group `you`.

`chown` changes the owner or group, usually like `chown newuser:newgroup file`. You will not run it in this lesson. On Linux, giving a file to another user **always needs `sudo`**, even for a file you own. An ordinary user cannot give a file away; only root can. (You can change a file's *group* with `chgrp`, but only to a group you belong to.) That is outside this no-sudo track. It matters once you manage a real server with several users.

There is a bigger idea under all of this: **least privilege**. Give each user and each file only the access it needs, and nothing more. A config file or credentials file that everyone can read or write is one of the first things auditors and attackers look for. Every permission left open beyond what is needed is a door that did not need to be unlocked.

### What to notice

- The permission string has four parts: type, owner, group, other. Each `rwx` group has a number built from 4, 2, and 1.
- `chmod` changes permissions symbolically (`u+x`, one change at a time) or numerically (`755`, the whole string at once).
- `whoami` and `id` tell you who you are. `/etc/passwd` lists every account, and only `root` should have user ID `0`.
- `chown` changes ownership and always needs root. Here it is a concept; you will use it later on real servers.
- Loose permissions are a routine finding in real security assessments, which is why least privilege matters.
