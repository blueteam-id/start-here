## What you now know

Six lessons ago, you had never opened a terminal on purpose. Here is what you covered since:

1. **What Is Linux, and Why It's Everywhere.** Linux is the kernel. A distro bundles it with tools and a package manager, and the two are updated on different schedules. Linux runs most of the servers, cloud workloads, and containers a defender works with.
2. **Getting Oriented in the Shell.** The shell sits between you and the kernel. The prompt tells you who and where you are, and whether you are root. `pwd`, `ls`, and `cd` are the first commands on any unfamiliar system, and `man` and `--help` are there when you forget an option.
3. **Navigating the Filesystem.** Absolute paths always mean the same place; relative paths depend on where you are. `/etc`, `/var/log`, and `/tmp` are worth knowing by heart. Dotfiles are a convention, not a security boundary. `rm` has no undo.
4. **Reading and Searching Files.** `cat`, `less`, `head`, and `tail` get you to the part of a file you need. `grep` finds the signal in a pile of log lines, `nano` edits a file, and `tail -f` watches one live.
5. **Permissions and Ownership.** The permission string has type, owner, group, and other. `chmod` changes it symbolically or with numbers. `id` and `/etc/passwd` show who exists on the system. A world-writable file is one of the first things a pentest report flags.
6. **Processes and Installing Software.** `ps` and `top` show what is running. `kill` asks a process to stop (politely, or with `-9` as a last resort). Package managers track what is installed, so an unexplained package stands out.

Reading a prompt, moving around, searching text, fixing permissions, and watching processes and packages: these are the daily reflexes of anyone who works on Linux systems. Everything later builds on them.

## Hands-on: triage a suspicious file

This exercise teaches nothing new. It chains commands from the whole track into one small scenario: a file shows up that you should not trust yet, and you work through it as you would on a real system.

Go back to your practice folder first. Everything below happens inside it:

```bash
cd ~/linux-essentials
```

A file arrives. Create a stand-in, and imagine you received it rather than typed it:

```bash
touch incoming-attachment.sh
```

Imagine that whatever dropped the file also left it wide open. That happens on real systems more often than you would like. Reproduce it on purpose, so there is something to catch:

```bash
chmod 777 incoming-attachment.sh
```

Check it the way you would check any file you were handed:

```bash
ls -l incoming-attachment.sh
```

You should see something like `-rwxrwxrwx 1 you you 0 ... incoming-attachment.sh`. Read it the way Lesson 5 taught you: owner, group, and other can all read, write, and execute it. A `777` on a file you have no reason to trust is exactly the kind of finding that gets flagged. Anyone on the system could rewrite it or run it. You just caught it.

Fix it. This file has no reason to be executable, or writable by anyone but you. Set it back to a sane default:

```bash
chmod 644 incoming-attachment.sh
ls -l incoming-attachment.sh
```

The second `ls -l` should show `-rw-r--r--`: you can read and write, everyone else can only read. Looking at the file before trusting it, then fixing it, is the whole habit in small.

The last step uses Lesson 4. Suppose a log recorded what just happened to the file. Create a small one:

```bash
cat > triage.log << 'EOF'
2024-03-02 09:00:01 INFO Session started
2024-03-02 09:02:17 INFO File received: incoming-attachment.sh
2024-03-02 09:02:18 ALERT permissions changed to 777 on incoming-attachment.sh
2024-03-02 09:05:44 INFO Session closed
EOF
```

Now search it for the line that matters, the way you would search a real `auth.log` or `syslog` for a known marker:

```bash
grep "ALERT" triage.log
```

That one line is what would start a real investigation: something made this file world-writable, and the log caught it. You walked the whole path: receive, inspect, catch a bad default, fix it, and confirm the story in the log. Several lessons of commands, one small scenario, and nothing outside `~/linux-essentials` touched.

## Where to go from here

This track stopped at foundation depth on purpose. Shells, paths, permissions, processes, and package managers are each topics people spend whole careers on: system administration, kernel internals, package security, process forensics. You now have the map, the vocabulary, and enough practice not to feel lost the first time a real server asks something of you.

If a command did not behave the way a lesson said, or you want to go deeper now, **bring it to the community Discord** with the Join Discord button at the top of the page. That is where harder questions get worked through, where people compare notes across distros and setups, and where beginner questions are always welcome. The question you write down in the reflection below is a good way to start.

When you are ready, the next tracks build on what you practiced here. <TrackLink slug="networking-fundamentals" /> picks up once a machine needs to talk to another one. Later tracks ask you to read logs, check permissions, and watch processes on systems that are no longer a safe sandbox. The habits you built in `~/linux-essentials` are the ones that carry over.
