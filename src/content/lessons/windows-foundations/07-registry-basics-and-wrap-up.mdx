## What the registry is

The **registry** is a database where Windows stores configuration: hardware settings, installed-software data, user preferences, and, most important for defenders, the settings that decide **what runs automatically**.

It is organized into a few top-level keys called **hives**. You will meet two constantly:

- **HKEY_LOCAL_MACHINE (HKLM)**: machine-wide settings, for every user on this computer.
- **HKEY_CURRENT_USER (HKCU)**: settings for whichever account is logged in now.

Under each hive, the registry branches into **keys** (like folders), which hold **values** (individual settings, each with a name, a type, and data). You can browse it with the built-in `regedit` app. For this lesson, use PowerShell instead, because reading from PowerShell is safer than clicking around:

```powershell
Get-ChildItem "HKCU:\Software" | Select-Object -First 10 Name
```

This lists the first ten subkeys under the `Software` key in your own user hive. Each one usually belongs to a program that stores its settings there.

## The Run keys: where attackers plant persistence

One pair of keys matters to a defender more than almost any other: the **Run keys**. They list programs Windows starts automatically every time a user logs in.

```powershell
Get-ItemProperty "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"
Get-ItemProperty "HKLM:\Software\Microsoft\Windows\CurrentVersion\Run"
```

The first shows your own autorun programs. The second shows the machine-wide list for every account.

On a clean personal machine, you will usually see a short, boring list: maybe a cloud-sync app or a hardware vendor's tray tool. That is the point. This list should be **short, boring, and explainable**.

Malware that wants to survive a reboot often adds itself to one of these keys. This is called **persistence**. That is why checking the Run keys is one of the first and fastest triage steps on a machine you suspect is compromised. An entry you cannot explain, pointing at a file in `%TEMP%` or another odd place, is the kind of finding that turns a routine check into a real incident.

This lesson never writes to these real keys; the exercise at the end uses a practice copy instead. On a real investigation, you would compare what you find against a **baseline** of what is normal for that machine, not edit anything in the moment.

## What you now know

Six lessons ago, you had never opened PowerShell on purpose. Here is what you covered since:

1. **What Is Windows, and Why It Matters for Defenders.** Desktop and server editions share one NT kernel. Active Directory is why one compromised Windows account can matter far beyond one machine.
2. **Getting Oriented.** PowerShell and cmd.exe can run side by side. The file system is built around drive letters and a few folders worth knowing (`Program Files`, `Users`, `%TEMP%`). `%TEMP%` is a common landing spot for dropped files.
3. **Permissions and Ownership.** NTFS ACLs name exact users and rights instead of three fixed categories. `icacls` and `Get-Acl` read them. UAC is the deliberate pause between a program running and a program getting admin control.
4. **Active Directory.** One domain controller manages logins and permissions for every computer in a company, like one badge office that opens every door. That is why one stolen Domain Admin account is so dangerous.
5. **PowerShell Essentials.** The pipeline passes objects, not text. `Where-Object` and `Sort-Object` filter and sort on real properties. A long, encoded PowerShell command line is a classic fileless-malware sign.
6. **Event Viewer and Windows Logs.** The Security log's 4624/4625 logon events, 4688 process events, and the alarming 1102 "log cleared" event are the backbone of most Windows triage.

Moving around confidently, reading permissions, understanding how Active Directory ties a company together, filtering real data with the pipeline, reading the Security log, and now checking autorun keys: these are the daily reflexes of anyone who triages Windows systems.

## Hands-on: triage a suspicious autorun entry

This exercise chains commands from the whole track into one small scenario: a machine shows signs of an unwanted program starting automatically, and you work through it as you would on a real system.

Go back to your practice folder first:

```powershell
Set-Location "$HOME\windows-foundations"
```

Simulate the dropped file. Imagine it arrived with a phishing attachment, not from a command you typed:

```powershell
New-Item -ItemType File -Path "$env:TEMP\update-helper.exe" -Force
```

Check its permissions the way Lesson 3 taught you:

```powershell
icacls "$env:TEMP\update-helper.exe"
```

You will see the ordinary permissions any file in `%TEMP%` gets. That is worth noticing in itself: your user can write here by design, which is exactly why it makes such a convenient drop point.

Now plant an autorun entry pointing at it. A real attacker would write to the real Run key from earlier in this lesson. You will not: if you stopped halfway through this exercise, Windows would try to launch that file at every login. Instead, create a **practice key** that copies the real key's shape, so everything you write lives in a place you own and can delete in one go:

```powershell
New-Item -Path "HKCU:\Software\windows-foundations-practice\Run" -Force
New-ItemProperty -Path "HKCU:\Software\windows-foundations-practice\Run" -Name "UpdateHelper" -Value "$env:TEMP\update-helper.exe" -PropertyType String -Force
```

Read it back the same way you read the real Run key:

```powershell
Get-ItemProperty "HKCU:\Software\windows-foundations-practice\Run"
```

That `UpdateHelper` entry points at a file in `%TEMP%`, with a generic name chosen to look routine. It is the pattern described earlier: an autorun entry you cannot explain, pointing at an unusual location. Now do the real check, read-only, on the actual Run key:

```powershell
Get-ItemProperty "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"
```

Can you explain every entry there? On a real investigation, an entry you cannot explain is the moment you escalate rather than assume.

Last, ask the Security log one triage question from Lesson 6: has anyone cleared it? This needs an **administrator** prompt, as Lesson 6 explained, so open one just for this command:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=1102} -MaxEvents 5 |
    Select-Object TimeCreated, Id
```

If it prints "No events were found that match the specified selection criteria", no "log cleared" event is recorded, which is what you want to see. If it says "Attempted to perform an unauthorized operation" instead, the prompt is not elevated, so the check did not actually run. If you do see a 1102 and cannot explain it, that is a finding on its own. Close the admin window afterward.

Clean up now, back in your normal prompt, so your machine is left exactly as it was before this exercise:

```powershell
Remove-Item "HKCU:\Software\windows-foundations-practice" -Recurse
Remove-Item "$env:TEMP\update-helper.exe"
```

You walked the whole path: a dropped file in a writable location, an autorun entry pointing at it, a read-only check of the real autorun list, and a check that the Security log has not been wiped. Several lessons of commands, one small scenario, and nothing written outside your own practice key and one temporary file.
