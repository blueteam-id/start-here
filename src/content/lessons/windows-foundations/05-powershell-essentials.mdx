## Verb-Noun: PowerShell's naming convention

Every PowerShell cmdlet follows one pattern: `Verb-Noun`. `Get-Process` gets processes. `Get-Service` gets services. `Stop-Process` stops a process. `Set-Location` sets your location.

Once you know the pattern, you can often guess a cmdlet's name before looking it up. When you cannot, PowerShell documents itself:

```powershell
Get-Command -Verb Get -Noun Process*
Get-Help Get-Process -Examples
```

- `Get-Command` searches for cmdlets by verb or noun.
- `Get-Help` prints a cmdlet's built-in manual, with examples, entirely offline.

Linux has `man` pages, but its command names (`grep`, `awk`, `ls`) do not follow a pattern you can guess. `Verb-Noun` does.

## The pipeline: objects, not text

This is the biggest difference from the Linux shell.

- A Linux pipe (`|`) passes **plain text** to the next command. That command has to cut the text apart again to use it. That is why tools like `grep`, `awk`, and `cut` exist.
- A PowerShell pipe also uses `|`, but it passes whole **objects**: structured data with named properties. The next cmdlet reads those properties by name. No text cutting needed.

See it for yourself:

```powershell
Get-Process | Get-Member
```

`Get-Member` lists every property and method of whatever came through the pipeline. You will see properties like `Id`, `ProcessName`, `CPU`, and `WorkingSet` (memory use). Because these are real properties, not columns of text, you can filter and sort on them directly:

```powershell
Get-Process | Where-Object { $_.WorkingSet -gt 100MB } | Sort-Object WorkingSet -Descending | Select-Object -First 5 ProcessName, WorkingSet
```

Read it left to right, like a Linux pipeline:

1. `Get-Process` gets every running process.
2. `Where-Object` keeps only those using more than 100MB of memory. `$_` means "the current object in the pipeline".
3. `Sort-Object` orders them by memory use, largest first.
4. `Select-Object -First 5` keeps the top five, showing only the two properties you asked for.

Every step worked with real numbers and names as data, not as text that had to be cut apart.

## A few everyday cmdlets

Run these from your `windows-foundations` folder, where `practice.txt` from Lesson 3 lives:

```powershell
Get-Process                    # what's running right now (like Linux's ps)
Get-Service                    # background services and their status
Get-Content .\practice.txt     # read a file's contents (like cat)
Get-ChildItem -Recurse         # list files recursively (like find, roughly)
```

Now filter `Get-Service` to show services that are not running:

```powershell
Get-Service | Where-Object { $_.Status -eq 'Stopped' } | Select-Object -First 10 Name, Status
```

## Execution policy, and why attackers like PowerShell

PowerShell has an **execution policy**: a setting that controls whether script files (`.ps1`) may run at all. It does not affect commands you type yourself. Check yours:

```powershell
Get-ExecutionPolicy
```

On Windows 10 and 11, the default is usually `Restricted`, which blocks scripts entirely. On Windows Server it is usually `RemoteSigned`: local scripts run, and downloaded scripts must be digitally signed. Your result may differ if an administrator or a program changed it.

The policy exists for a defensive reason. PowerShell is very powerful. From one command, it can touch files, the registry, the network, and other processes, without ever writing a normal `.exe` file to disk. Antivirus tools often look for suspicious files, so this makes PowerShell attractive for **fileless malware**. A single obfuscated or base64-encoded one-liner, often run with flags like `-EncodedCommand` or `-WindowStyle Hidden`, can download and run more malicious code entirely in memory.

That is also why defenders never treat "PowerShell ran" as routine. Modern Windows can log PowerShell activity in detail (**Script Block Logging**, separate from the Event Viewer work in the next lesson), because so much real attacker activity runs through it. Knowing the shell well is what lets you notice when something run through it looks wrong.

### What to notice

- The PowerShell pipeline passes objects, not text. That is why `Where-Object` and `Sort-Object` can work on real properties without a text-parsing tool.
- `Get-Help` and `Get-Command` make PowerShell self-documenting, offline. Use them instead of guessing.
- A long, encoded, or obfuscated PowerShell command line is a classic sign of fileless malware, and exactly what PowerShell logging exists to capture.
