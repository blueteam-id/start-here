## What the Windows Event Log is

Linux usually keeps logs as plain text files, like `/var/log/auth.log` and `/var/log/syslog`, the kind of file you searched with `grep` in Linux Essentials. Windows keeps logs in a structured, binary format called the **Windows Event Log**. You read it with the built-in **Event Viewer** app, or query it from the command line.

Every event is a structured record with:

- a timestamp,
- a source,
- a severity level,
- a numeric **Event ID** that says exactly what kind of thing happened. This is the most useful part.

Three logs matter most for everyday defensive work:

- **Application**: events logged by installed software.
- **System**: events logged by Windows and its drivers, such as a service failing to start or a disk reporting errors.
- **Security**: logon attempts, privilege use, and other audit events. A defender opens this one first in almost every investigation.

### Before you start: this lesson needs an administrator prompt

The Security log holds sensitive information, so Windows only lets administrators read it. This is the UAC idea from Lesson 3 in action. For this lesson:

- **Event Viewer:** if your account is an administrator (you checked with `whoami /groups` in Lesson 3), Event Viewer can open the Security log for you.
- **PowerShell:** a normal prompt is not enough, even on an administrator account. Right-click the Start button and choose **Terminal (Admin)** on Windows 11, or **Windows PowerShell (Admin)** on Windows 10, then click **Yes** on the UAC prompt. The window title now starts with "Administrator".

If a command below fails with "Attempted to perform an unauthorized operation", your prompt is not elevated. Close it and open an admin one. If your account is a standard user, you cannot read the Security log at all; you can still follow along by replacing `Security` with `System` in the commands, which shows the same structure with different events.

Everything in this lesson only **reads** logs. Close the admin window when you finish, so you are not left running with more privilege than you need.

Open Event Viewer now (search for it in the Start menu). In the left pane, expand **Windows Logs** to see all three logs. Click **Security**. You will see a long list of entries, each with a timestamp and an Event ID column.

## Event IDs worth recognizing on sight

A few Security log Event IDs come up so often that they are worth knowing by heart:

- **4624: an account logged on successfully.** Routine on its own; an active machine has dozens. The *pattern* is what matters. A 4624 from a place or at a time that does not fit how the account is normally used deserves a second look.
- **4625: an account failed to log on.** A few of these happen to anyone who mistypes a password. A *burst* of 4625s for the same account in a short time is the classic sign of a brute-force or password-guessing attack.
- **4688: a new process was created.** This only appears if process-creation auditing is turned on, which is not the default everywhere. It shows which program ran and with what command line, like the `ps` habit from Linux Essentials.
- **1102: the audit log was cleared.** This one stands out. An attacker with enough access to clear the Security log is trying to erase evidence. A 1102 is one of the strongest single warning signs a Windows log can show, because honest reasons to clear a production audit log are rare.

## Querying logs from PowerShell

Event Viewer is fine for a quick look. When you are looking for something specific, PowerShell filtering works much better. `Get-WinEvent` queries any log directly:

```powershell
Get-WinEvent -LogName Security -MaxEvents 20 | Select-Object TimeCreated, Id, Message | Format-List
```

That pulls the 20 most recent Security log entries. Now filter for the events that matter most, successful and failed logons, using a **filter hashtable**:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624,4625} -MaxEvents 15 |
    Select-Object TimeCreated, Id, Message |
    Format-Table -Wrap
```

Read it like the pipeline in Lesson 5:

1. `Get-WinEvent` reads from the Security log.
2. `-FilterHashtable` narrows the query to Event IDs 4624 and 4625. The query itself does the filtering, which is much faster than pulling everything and filtering afterward with `Where-Object`.
3. The rest formats the output so you can read it.

On an ordinary desktop you will mostly see your own 4624 logons. If there were any failed logins, even your own mistyped passwords, you will see 4625s mixed in, each with a timestamp.

To see only the failures, and practice spotting the brute-force pattern:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625} -MaxEvents 15 |
    Select-Object TimeCreated, Message
```

If this prints "No events were found that match the specified selection criteria", nobody has failed to log on recently. That is a normal, good result, not an error in the command.

### What to notice

- One 4625 is nothing. Many 4625s for the same account, close together, is the pattern that matters. Think in bursts, not single events.
- Event ID 1102 (audit log cleared) is close to a worst-case single event. It usually means someone with real access tried to cover their tracks.
- `Get-WinEvent -FilterHashtable` filters at the source instead of pulling everything first. On a busy server with a huge log, that matters a lot.
